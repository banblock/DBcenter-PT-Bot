Fleet Node · 로봇 상태 퍼블리시 검증

Fleet은 로봇 상태를 어디까지 아는가

UI팀이 준 robot_state 15개 상태 중 Fleet Node가 지금 실제로 판정하는 건 IDLE / PATROLLING / DISPATCHING 3개뿐입니다. 미션 배정 여부와 이상신호 대응 여부만으로 판정하고, 1Hz 폴링으로 변화가 있을 때만 /control/<robot>_State에 퍼블리시합니다. 아래는 test_robot_status.py에 정의된 시나리오를 robot_status.py로 실제 실행한 결과입니다.

Fleet이 판정하는 상태 3개 / UI 전체 어휘 15개 시나리오 2개 + 우선순위 케이스 3개 생성 시각 2026-08-08 23:38

신규 로봇 등장 → 순찰 시작 → 이상신호 대응 → 순찰 복귀

robot3가 아직 구역을 못 받았을 때(IDLE)부터 시작해서, Backend가 구역을 배정하면 PATROLLING으로, 이상신호 트리거로 dispatch되면 DISPATCHING으로, _on_anomaly_done을 받으면 다시 PATROLLING으로 바뀐다. 같은 상태가 유지되는 폴링 tick(3번째 step)에서는 퍼블리시가 일어나지 않아야 한다 - 1Hz 타이머가 매초 무조건 쏘면 안 되고 변화가 있을 때만 쏴야 하기 때문.

구역 재배정으로 미션이 사라지면 IDLE로 돌아감

robot8이 순찰 중(PATROLLING)이던 도중 Backend가 구역 구성을 바꿔서 robot8에게 배정된 구역이 없어지면(예: 2대 구성에서 1대로 축소), 다음 폴링 tick에 missions에서 robot8이 빠지고 IDLE로 떨어져야 한다.

우선순위 케이스

compute_status()의 우선순위 규칙(이상신호 대응 > 미션 보유 > 둘 다 아님)이 의도대로 동작하는지 확인.

  • 검증됨 이상신호 대응이 미션 보유보다 우선

    robot3가 missions에도 있고 anomaly_busy에도 있을 때 -> DISPATCHING. 결과: DISPATCHING

  • 검증됨 미션 없이 anomaly_busy만 있어도 DISPATCHING

    robot9가 missions에는 없고 anomaly_busy에만 있을 때 -> DISPATCHING. 결과: DISPATCHING

  • 검증됨 미션도 이상신호 대응도 없으면 IDLE

    robot8이 missions에도 anomaly_busy에도 없을 때 -> IDLE. 결과: IDLE
